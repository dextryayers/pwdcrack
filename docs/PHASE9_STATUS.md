## P9.1.01 the cluster listened to the world

`DistributedConfig::default` bound to `0.0.0.0:5555`. `Handshake` carried no
credential. A master started with no arguments therefore listened on every
interface and admitted any peer that connected.

### What replaced it

`engines/engine-distributed/src/netpolicy.rs`. `BindPolicy::resolve` returns the
address and what the caller should warn about, and refuses in two separate cases:

- a routable address that was not explicitly requested,
- a routable address that was explicitly requested but has no token.

Two distinct refusals rather than one, because they are different mistakes. Naming
`0.0.0.0` by accident is common and deserves a prompt refusal. Naming it
deliberately and still having no credential is a decision that deserves a
different, louder refusal.

`0.0.0.0` and `[::]` are both treated as exposed. `0.0.0.0` binds every interface,
which is the case that has to be caught, and treating it as safe because it is not
a specific address would miss it.

### Verified by execution

```
$ pwdcrack --distributed --bind 0.0.0.0:5555 dictionary h.txt w.txt
[!] distributed: refusing to bind 0.0.0.0:5555: it is not a loopback address.
Pass --bind 0.0.0.0:5555 to accept it, and --token to put a shared secret on the cluster.
$ echo $?
1

$ pwdcrack --distributed dictionary h.txt w.txt
[*] Cracked 1/1 hashes
  8350c7ecc6d4706e12107df747eb6e71  ->  pwdcrack-reference-candidate  [Md5Hash]
```

The flags are `--bind`, `--token`, `--allow-exposed-bind` and `--master`. The
token may come from `PWDCRACK_CLUSTER_TOKEN` instead, which keeps it out of the
process list where every other user on the machine can read it.

## P9.1.03 a token that nothing checked

`ClusterAuth` computed correct answers and nothing called it. Worse than dead
code: the flag existed, the help text implied a credential, and a peer that had
never heard of the cluster could connect and be entered into the worker table.

`handle_worker` accepted a TCP connection and immediately interpreted whatever
arrived. A peer could name itself anything and receive work units.

### The handshake

```
master -> worker   Challenge { nonce }      fresh per connection, always sent
worker -> master   Authenticate { response }  SHA-256(token || nonce)
worker -> master   Handshake { .. }          only after the above succeeds
```

The nonce is generated by the master and travels on the wire. The first
implementation had both sides generating a nonce independently, which cannot work:
they would never match, and the integration test `a_worker_with_the_token_is_accepted`
failed on exactly that. The test found the design error, not a test error.

Binding the response to a per connection nonce is what makes a captured response
worthless elsewhere. `a_replayed_response_from_another_nonce_is_refused` sends a
response computed over a different nonce and asserts the peer is not registered.

### Enforced at one place

`AdmissionGate::on_message` is consulted before any frame is interpreted, so
there is exactly one place a peer can enter. `Admission::Rejected` ends the
connection; `AwaitingAuthentication` ends it too, with a message naming the frame
that arrived too early.

### Verified over a real socket

`engines/engine-distributed/tests/admission_over_socket.rs`, 5 tests:

| Test | Asserts |
|------|---------|
| `a_worker_without_the_token_is_disconnected_before_it_is_registered` | no credential, no entry in the worker table, no `AssignWork` |
| `a_worker_with_the_token_is_accepted` | correct credential, peer registered |
| `a_worker_with_the_wrong_token_is_refused` | wrong credential, peer not registered |
| `an_open_cluster_accepts_a_peer_with_no_credential` | a tokenless cluster still works |
| `a_replayed_response_from_another_nonce_is_refused` | a stale response admits nobody |

These call the same `handle_worker` the accept loop uses, through
`serve_connection_for_test`. A test that reimplemented the gate check would prove
nothing about the handler, which is why the handler is exposed instead.

### What this is not

A shared token over plaintext TCP is not mutual authentication in the sense
P9.1.03 means alongside P9.1.02. It stops a peer that does not hold the token from
joining. It does not encrypt the traffic, so a host on the same network can read
every work unit, which for a wordlist path is most of what it needs. P9.1.02 is
still required before this runs anywhere but loopback.

## P9.1.05 the worker opened whatever path it was told

`WorkUnit::AttackType::Dictionary` carried a `wordlist_path: String` and the
worker ran `File::open(path)` on it. No validation of any kind.

The path comes from the master, and a master is a peer rather than a supervisor.
With an unchecked path that peer chooses which file the worker opens. It does not
get the contents back directly, but the bytes flow: the worker tests them as
candidates against the target hashes and the match set returns in
`Message::Result`. Reading a private key that way is a real extraction channel.

### The rule

`engines/engine-distributed/src/wordlist.rs`. A worker opens only paths under
directories the operator granted locally, with `--wordlist-dir`. The master picks
a file inside the grant; it cannot widen the grant.

With no grant given, a worker **refuses every dictionary unit** and logs a
warning. The previous default was the opposite, and that default is the defect.

Two properties that are easy to get wrong and are both tested:

- **Resolution before the check.** A lexical prefix test accepts
  `/granted/../private/id_rsa`, and then opens something outside the grant.
  `resolve` canonicalises first, so the path compared against the roots is the
  path that gets opened.
- **Symlinks.** A link inside the granted directory pointing out of it resolves to
  its target, and the target is what is tested.

Containment is component-wise, not string prefix. `/data/wl` is not a parent of
`/data/wlx` even though one string starts with the other.

### Verified by execution

```
ALLOW  ok.txt            -> /tmp/opencode/grant-test/wl/ok.txt
DENY   ../private/id_rsa -> not a relative path, so it could not be checked
DENY   /etc/passwd       -> not a relative path, so it could not be checked
DENY   nice.txt          -> /tmp/opencode/grant-test/private/id_rsa resolves to
                            /tmp/opencode/grant-test/private/id_rsa, which is
                            outside the granted wordlist directories
```

The fourth line is the interesting one: `nice.txt` lives inside the granted
directory and is a symlink, and it is refused because of where it points.

### The unguarded read is gone

`read_wordlist_lines` in `worker.rs` was removed, not left unused. A free function
that opens a path with no checks is one refactor away from being called again.

### The other half of P9.1.05

The plan also allows sending contents or a digest plus a manifest instead of a
path. `WordlistManifest` provides that primitive: a size and a SHA-256, verified
before use, with a test that flips every bit of the payload and asserts the digest
changes. Nothing sends manifests yet; the path policy is what is enforced today.

## P9.1.02 TLS

Not done. `tokio-rustls` is not a dependency and generating a self signed
certificate needs either `rcgen` or the `openssl` command line. Neither is
available here, and adding two dependencies plus certificate generation logic that
cannot be exercised against a real peer would be code that has never run.

Until it is done, the cluster must stay on loopback. `BindPolicy` enforces that
the address is loopback unless a token is present, but a token is not encryption,
so the honest statement is: **do not expose this port**.

## P9.2.02 heartbeat and P9.2.03 checkpoint, partly present

Both exist and neither has been verified here.

The reaper requeues orphaned work after 30 seconds without a heartbeat, which is
not the "three missed heartbeats with exponential backoff" the plan asks for. The
checkpoint writes JSON every 15 seconds to `/tmp`, which is world readable on a
shared machine and lost on reboot. Neither is claimed as complete.

## Defects found after the first pass, while Phase 10 and 11 were being done

Three, all in code this phase had introduced, all found by tests that had been
green before.

**The wordlist manifest could never verify.** `WordlistManifest` was built from
the file's bytes and checked against `words.join("\n")`, where `words` came from
`lines()`. Splitting a file that ends in a newline and joining it with `\n` loses
that newline, so the reconstructed content was exactly one byte shorter and every
submission failed with "expected 20 bytes, got 19". The manifest now carries a
`trailing_newline` flag and `WordlistManifest::render` rebuilds the content
faithfully. Nothing in the suite had registered a wordlist through a master, which
is why this survived.

**A test asserted something false.** `every_listed_spelling_verifies` looped over
every entry in `SUPPORTED` for every case, so it required "SHA1" to verify an MD5
digest. It failed on that, which hid the real fault underneath: the MD4 constant
in the same test was `afe04867ec7a3845145579c95f8dbfb7`, which is not the MD4 of
anything. Recomputing all five digests against oracles gave
`866437cb7a794bce2b727acc0362ee27` for MD4 of "hello"; the other four were right.

**A test did not compile.** `every_listed_spelling_verifies` iterated
`SUPPORTED: &[(&str, &[&str])]` directly, so the pattern destructured the slice
reference and `spellings` bound as `&&[&str]`. Plain `cargo test -p
engine-distributed` failed to build with "`&&[&str]` is not an iterator". The file
had been correct at some point and was not being compiled, because nothing ran it.

The pattern is the same in all three: a value that nobody checked against
anything, behind a test that could not fail for the right reason.
